## 宿題

- 取り組んだレベル：発展
- やったこと：
  - 対象：SWE-bench Verified（https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified ）
  - Hugging Face の Dataset Viewer で全 500 件の内訳を見て、難易度の違う 4 件の問題文・正解のパッチ・採点用のテストを読んだ
  - 作り方と検証の手順は、OpenAI の公式ブログ「Introducing SWE-bench Verified」（2024/8/13、https://openai.com/index/introducing-swe-bench-verified/ ）と、元の SWE-bench の論文（C. E. Jimenez et al., ICLR 2024, arXiv:2310.06770）で調べた
- 結果：
  - データセットの中身
    - 1 件 = 実際の GitHub の issue（問題文）＋ その時点のリポジトリ ＋ 採点用のテスト。モデルはリポジトリのコードを直す修正（パッチ）を出す
    - 500 件、12 リポジトリ。django 231 件、sympy 75 件、sphinx 44 件、matplotlib 34 件、scikit-learn 32 件 など
    - 人が見積もった難易度：15 分未満 194 件、15 分〜1 時間 261 件、1〜4 時間 42 件、4 時間超 3 件
  - 読んだ問題の要約
    - django-10880（15 分未満）：Count 集計で distinct と条件式を組み合わせると、生成される SQL の「DISTINCT」の後ろに空白が抜けて構文エラーになる。正解は文字列に空白を 1 つ足すだけ（1 行）。自分でも、エラーの SQL を見れば解ける。LLM にとって難しいのは、巨大な django の中から、SQL を組み立てている場所を探し当てることだと思う
    - django-12143（15 分〜1 時間）：管理画面で、フォームセットの接頭辞に正規表現の特殊文字が入ると、正規表現の組み立てが壊れてデータを失うおそれがある。直し方（re.escape）は issue に書いてあるので、自分でも解ける。答えがほぼ書いてある問題も含まれていると分かった
    - astropy-12907（15 分〜1 時間）：入れ子になった合成モデルで、分離可能性の行列が正しく計算されない。正解は、行列を「1」で埋めていた 1 行を、右側の行列そのものを入れるように直す修正。自分では、行列の意味（どの入力がどの出力に効くか）を理解しないと原因に気づけず、すぐには解けない。LLM にとっても、ドメインの知識と、短い差分で済む場所の特定が難しい
    - sympy-13878（4 時間超）：連続分布のうち、積分で累積分布関数（CDF）がうまく求まらない十数種類について、CDF の式を直接実装してほしいという依頼。正解のパッチは約 470 行で、14 の分布に式を足している。各分布の数式を正しく書く必要があり、自分では数時間でも難しい。テストは CDF を記号の式で完全一致させるので、数学的に同じでも書き方が違う式は落ちるおそれがあると感じた
  - 作った人と手順
    - 元の SWE-bench（2,294 件）：人気の Python リポジトリ 12 個から、issue を解決し、かつテストを追加しているプルリクエストを自動で集めた。さらに、実行して「修正前に落ちて修正後に通るテスト」が 1 つ以上あるものに絞った。作問は人の手ではなく、実際の開発の記録をそのまま使っている
    - Verified：OpenAI が Python 経験のあるソフトウェア開発者 93 人に依頼し、元のテストセットからランダムに選んだ 1,699 件を確認した。1 件につき 3 人が別々に判定した
    - 判定の観点は 2 つ。① issue の問題文があいまいで解き方が決まらないか、② 採点用のテストが正しい解答まで落としてしまわないか。それぞれ 0〜3 の 4 段階で付け、3 人のうち最も厳しい値を採用し、2 以上（深刻）なら外した。あわせて難易度（修正にかかる時間）も見積もった
    - 結果、68.3% が除外された（問題文があいまい 38.3%、テストが不適切 61.1%。重複あり）。残った中から、15 分未満 196 件と 1 時間超 45 件をすべて入れ、残りをランダムに選んで 500 件にした（公開データでは 15 分未満が 194 件で、ブログの値と 2 件ずれていた）
  - 採点の方法：テストの実行（コード）。人の修正で追加された FAIL_TO_PASS のテストが通り（issue が直った）、かつ元からある PASS_TO_PASS のテストも通る（ほかを壊していない）ときだけ合格。人も LLM も採点に入らない。読んだ 4 件では、FAIL_TO_PASS が 1〜2 個、PASS_TO_PASS が 13〜142 個だった
  - 今日の評価セットとの違い

    | 軸 | 今日の演習の評価セット | SWE-bench Verified |
    |---|---|---|
    | 規模 | 10 件 | 500 件（元は 2,294 件。1,699 件を確認して絞った） |
    | 作問 | 講師 1 人が、エッジケースを狙って作った（失敗をわざと混ぜた） | 実際の GitHub の issue と修正の記録から自動で集めた |
    | 検証の人数 | 講師 1 人。受講生が各自でラベルを付け、講師と比べた | 開発者 93 人。1 件につき 3 人が独立に判定し、最も厳しい判定で外した |
    | 採点 | 人と LLM（4 基準）、コード（回の表示） | テストの実行のみ（コード） |
    | 合否の形 | 基準ごとに T / F / unsure | テストが全部通れば合格、の 1 つ |
    | 基準のあいまいさ | 「まだ決めていないこと」を残し、読みながら決める | 問題文があいまいなものは除外して、判定が割れないものだけ残す |

- 気づき・疑問：
  - SWE-bench は「テストの実行で合否が決まる」ので採点は機械的だが、そのぶん「テストが正しい解答を落とさないか」「問題文だけで解けるか」を人が確かめる手間がかかっていた。今日の評価セットは逆に、採点（人と LLM の判定）がぶれるので、ラベルの照合と基準の手直しに手間がかかった。どこかで人の確認が必要になる点は同じだと感じた
  - 3 人のうち最も厳しい判定を採用して外す、というやり方は、判定が割れたケースを捨てて「誰が見ても同じ合否になるケースだけ残す」ということで、講義の「良いケースとは、2 人が独立に判定して同じ合否になるケース」と同じ考え方だった。今日の演習では割れたケースを捨てずに、基準を書き足して決めた
  - 93 人で 3 重に確認しても、講義資料によると、OpenAI は 2026/2 に、o3 が安定して解けなかった 138 問の約 6 割にテストか問題文の不備があったとして、報告をやめている。sympy-13878 のように記号の式の完全一致で採点する問題は、正しい別解を落としうると思った。検証にどれだけ人をかけても採点器は間違うので、満点に近づいたら正解の側を疑う必要がある
  - 疑問：難易度は「人が直すのにかかる時間」で付けているが、LLM にとっての難しさ（探すファイルの多さ、ドメインの知識）と一致するのか。1 行で直る astropy-12907 のような問題が、LLM にとって本当に易しいのかを知りたい
